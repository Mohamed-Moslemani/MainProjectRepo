Slide 2 · The problem non technical

Renewing a Lebanese ID is a full day affair.

Today, citizens travel to a mukhtar, then a GDGS centre, then back, often across multiple districts. There is no online intake, no validation before the visit, no tracking. A bad photo means a second trip.

Slide 9 · AI pipeline technical

Six stages. Every output traced.

1. OCR             Google Cloud Vision
                   + LB specific field regex
                   + MRZ parser (LR biometric)

2. Quality gate    cv2: blur, glare, skew, resolution
                   retake reasons surface to citizen

3. LLM extraction  GPT-4o-mini (vision + text)
                   structured JSON for civil registry
                   used as fallback when regex fails

4. Face match      Rekognition CompareFaces
                   liveness fallback when reference
                   face cannot be extracted

5. Liveness        Rekognition Face Liveness
                   plus heuristic fallback

6. Reconciliation  declared fields vs OCR fields
                   plus cross document coherence
                   (LLM scored, fuzzy match)

7. Risk score      OCR 15, face 20, liveness 20,
                   reconciliation 25, quality 10,
                   severity 10

Decision bands

≤ 25  auto approve

25 to 60  manual review

> 60  reject with reasons

Conservative on purpose. Borderline is a human's job, not a model's.

Auditable by construction

  • Langfuse trace + span per stage
  • Risk breakdown persisted on the case row
  • Audit log per decision, indexed by case_id
  • Mukhtar attestation: three explicit booleans, contract tested

Slide 10 · LLMs in the pipeline technical

Vision LLM where regex fails. Nowhere else.

Model and role

  • GPT-4o-mini (vision capable, structured JSON output).
  • Sent both the OCR text and the original image bytes.
  • Fallback only: triggered when regex extracts fewer than OCR_LLM_FALLBACK_MIN_FIELDS.
  • Per-document-type schemas with explicit bilingual cell labels (الاسم, الشهرة, اسم الأب, إسم الأم وشهرتها).

Why a vision LLM, not just OCR

  • Civil registry extracts (بيان قيد إفرادي) are 3-column tables with labels and values in different cells.
  • Google Vision returns cells in geographic line order, which breaks any label[:\s]+value regex.
  • The LLM reasons over both modalities and returns the canonical field names downstream code already uses.

LLM as referee

  • Cross-document coherence: LLM checks all uploaded docs describe the same person (fuzzy match + structured comparison). Mismatch hard rejects with per-pair findings.
  • Reconciliation skip-list excludes citizen-typed metadata (sect, address, marital status) so the LLM is never blamed for missing what was never on the document.

Cost & safety

  • ≈ $0.005 per civil registry extract.
  • Passport MRZ flows never call the LLM (regex handles them cheaply).
  • Errors are non-fatal: empty dict returned, regex result wins.
  • Every call writes tokens_in, tokens_out, duration_ms, model to Prometheus and Langfuse.

Slide 11 · OCR & quality gate technical

Cheap, deterministic, gated.

Provider: Google Cloud Vision

  • Best Arabic + handwritten accuracy on real LB samples.
  • ≈ $0.0015 per page, no provider lock-in (only google_ocr.py imports it).
  • Mock mode for CI: deterministic fixtures, zero API cost.

Field extraction

  • field_extractor.py: regex-based, per document type.
  • mrz_parser.py: ICAO 9303 with checksum validation.
  • doc_classifier.py: routes to the right extractor.
  • ai_extractor.py: LLM fallback (slide 10).

Quality gate (cv2)

  • Blur (Laplacian variance), glare (% saturated pixels), skew (Hough lines), resolution.
  • Each metric has a calibrated threshold.
  • Failures emit typed retake reasons surfaced in the citizen UI.

Spoof detection

  • spoof_detector.py: heuristics for printed/screen recapture.
  • Result feeds risk severity weighting.
  • Anti-spoof Grafana dashboard tracks fail rate over time.

Slide 12 · Face & liveness technical

Managed liveness, audited similarity, smart fallback.

Provider: AWS Rekognition

  • CompareFaces: similarity score + bounding boxes.
  • Face Liveness: managed anti-spoof video session.
  • Threshold: 0.80 default (tunable per service type).

The reference-face problem

  • For id_new + passport_new, the only photo is the civil registry extract.
  • Rekognition often fails to find a face on a registry extract.
  • Old behaviour: charged 100% face-risk. False rejections.
  • New behaviour: if reference face missing AND liveness passed, fall back to liveness confidence as the face signal. Audit logged.

Heuristic fallback

  • If Rekognition is unreachable, a heuristic liveness check runs locally.
  • Lower confidence ceiling, marked in audit log as heuristic_liveness.
  • Risk score bumped accordingly.

Mock mode

  • FACE_MOCK_MODE=true for CI.
  • Deterministic similarity by file hash so tests reproduce.

Slide 13 · Reconciliation & risk scoring technical

Where the AI decision actually gets made.

Reconciliation

  • Declared fields vs merged OCR fields, normalized (Unicode + Arabic shaping + digit folding).
  • Fuzzy match (rapidfuzz) for names; exact for dates and numbers.
  • Skip list: renewal_reason, passport_validity_years, marital_status, address, phone, religious_sect, municipality.
  • Mismatched fields written back as retake_reasons["_reconciliation"].

Cross-document coherence

  • ≥ 2 identity documents must describe the same person.
  • cross_doc_check.py compares pairwise.
  • Hard reject on mismatch (canonical fraud pattern).
  • Per-pair findings recorded in audit log.

Risk score (weighted)

risk = 100 - (
  ocr_confidence       × 0.15 +
  face_similarity      × 0.20 +
  liveness_confidence  × 0.20 +
  reconciliation_score × 0.25 +
  quality_score        × 0.10 +
  severity_score       × 0.10
)

Each component is on [0,1]. Severity penalises spoof + cross-doc mismatches. Final score is in [0,100]; lower is safer.

Decision logic

  • ≤ 25 → auto approve (clean cases sail through).
  • 25–60 → manual review, audit log manual_review_required.
  • > 60 → reject with typed reasons.
  • Passport cases: extra hop to PENDING_MUKHTAR before approval.

Slide 14 · Traceability technical

Every AI decision is replayable.

Sample Langfuse trace (one case)

case.process case_id=c8a4 service=passport_new decision=auto_approve risk=18 ├─ ocr.extract doc=passport conf=0.93 fields=7 ok │ └─ ocr.mrz_parse format=LR checksum=valid ok ├─ ocr.quality blur=420 glare=0.12 skew=2° pass ├─ ocr.llm_extract model=gpt-4o-mini doc=civil_registry │ tokens_in=1842 tokens_out=312 cost=$0.0048 dur=1.7s 12 fields ├─ face.compare sim=0.87 threshold=0.80 match ├─ face.liveness conf=0.94 live ├─ recon.declared_vs_ocr matched=11/12 mismatched=0 clean ├─ recon.cross_doc pairs=3 coherent=true ok ├─ registry.lookup status=found conf=0.96 ok └─ risk.score breakdown={ocr:3,face:2,liveness:2,recon:6,qual:2,sev:3} 18

Trace, score, and ground truth label persist together. A reviewer can replay any case, swap a threshold, and rerun.

Three layers of evidence

  • Langfuse: per-stage spans, LLM tokens, cost, latency, custom scores (recon, face, liveness, risk, spoof, cross_doc).
  • Postgres audit_logs: typed events per case (state change, manual_review_required, registry_degraded_mode, attestation booleans).
  • Prometheus: counters, histograms, drift gauges scraped by Alloy and Grafana Cloud.

Mukhtar feedback as ground truth

Each mukhtar decision (and clerk override) writes back as a Langfuse score on the case trace. Aggregates per name across all cases automatically. The system's own labels are the eval set.

Slide 19 · Reliability, edge cases & tradeoffs technical

Where it bends, and how it's caught.

Reliability primitives

  • gateway_cron sidecar: outbox sweep every 60 s, mukhtar SLA escalation hourly. Restart-policy unless-stopped.
  • Idempotency table: per-key cached responses for case mutations and Stripe webhooks.
  • Partial unique index on appointment slots prevents double-booking races.
  • Registry-degraded mode: outage routes to neutral score + registry_degraded_mode audit, never to mass rejections.
  • Email outbox pattern: state change → row inserted → cron sweeps → SMTP. No lost mails on crash.

Tradeoffs (deliberate)

  • LLM: regex first, GPT-4o-mini fallback. Deterministic where possible, paying only where needed.
  • Face: AWS Rekognition. Managed liveness ≫ DIY MediaPipe for thesis scope.
  • OCR: Google Cloud Vision. Best Arabic accuracy, cheap.
  • Payments: Stripe Checkout. Hosted page = no PCI scope.
  • Risk thresholds: 25 / 60 conservative. False approve is worse than manual review.
  • Single-DB: gateway owns the schema. One ACID source of truth.

Evidence (real LB documents)

Slide 20 · Closing non technical

What problem? How? What are the limits?

What problem

Lebanese citizens lose a day or several renewing an ID or passport. There is no online intake, no validation before the visit, no tracking, and bad photos mean repeat trips.

How it works

Four-service AI pipeline (OCR, vision LLM fallback, face, liveness, reconciliation, risk) with mukhtar digital stamp for passports. Auto approve clean, route borderline, reject with reasons. Every call traced in Langfuse, scored, and replayable.

Limits

Civil registry is a mock. National-portal SSO not integrated. Small real-document corpus. Solo project, so no PR-review trail (commit messages compensate).

"Auto approve the easy 70%. Route borderline cases to humans. Reject with retake reasons, never silently. Make every decision replayable in Langfuse and visible on Grafana."
